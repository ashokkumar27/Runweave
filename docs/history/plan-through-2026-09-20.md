# Independent Agents API

Build a self-hosted API that runs tool-using agents across supported model providers. Start with one developer and one workspace; validate provider capabilities rather than promising every model supports every feature.

## Stack and boundaries

Python, FastAPI, PydanticAI, PostgreSQL, and Temporal. One repository, with API and worker processes. Use Docker Compose for local services and OpenTelemetry for run traces. Pin dependency versions after a compatibility spike.

Own the public Agent, Session, Run, and Event schemas. Keep PydanticAI behind a small runtime adapter. PostgreSQL stores application records and replayable events; Temporal owns workflow execution history. Add Harness capabilities individually when needed.

## Milestones

1. **Validate the foundation.** Run the same typed tool and structured-output task against two providers. Exercise PydanticAI's Temporal integration with a worker restart. Record supported versions and limitations. Done when both provider paths and recovery work in a small integration demo.
2. **Ship one complete API flow.** Implement create/get run, session continuation, and SSE events. Snapshot agent configuration per run. Persist ordered event IDs and support reconnect from the last received ID. Use explicit provider/model selection. Done when a client submits a task, sees tool progress, reconnects, and retrieves its result.
3. **Make execution reliable.** Add idempotent submission, bounded retries/timeouts, cancellation, approval and resume. Use stable workflow IDs plus recoverable dispatch to bridge database writes and Temporal starts. Deduplicate event writes and tool operations; external side effects require idempotency support or reconciliation. Done when fault tests cover worker crashes, duplicate requests, interrupted tool calls, and approval across restarts.
4. **Make it usable daily.** Add API-key authentication, usage limits, redacted traces, one MCP integration, and a small repeatable task evaluation set. Add a single isolated sandbox backend only when shell/file execution is needed. Done when the deployment guide reproduces a working installation and the evaluation set passes agreed thresholds.

Defer automatic model routing, subagents, persistent memory, a dashboard, multiple sandbox providers, and multi-tenancy until real usage establishes the need.

## Development workflow

Implement one milestone as small end-to-end changes. Each change states observable acceptance criteria, updates relevant tests, and leaves a runnable demo. Use fake models in default tests and opt-in provider integration tests. Keep setup and verified commands in README.md; record architectural decisions here until separate decision records are useful.

## Implementation decisions

- A single workspace admission row serializes the short submission transaction. A session accepts one active run; concurrent continuation receives 409. Only completed turns advance private session history, capped at 250 KB. This avoids ambiguous history forks without adding queues per session.
- The worker process also polls the transactional outbox and reconciles unexpectedly closed workflows. PostgreSQL stays authoritative for public status. Cancellation wins when it acquires the run lock first; a completed run cannot later become cancelled. Outbox commands remain recoverable while the worker is down.
- The current supported PydanticAI `TemporalDurability` capability runs the agent loop inside the deterministic workflow and registers model/tool I/O activities. Connection-free model metadata is used in workflows; provider clients are constructed and closed outside workflows through the private registration resolver. Credentials never travel in workflow dependencies or public events. Public schemas contain no PydanticAI/Temporal types.
- The MVP streams durable lifecycle/tool events, not model tokens. Approval uses PydanticAI deferred calls with persisted immutable decisions and outbox signals. Active time is cumulative across execution, retries and all resumes, and pauses only during durable approval waits. A finite operator approval allowance is snapshotted per run and shared across rounds (default 24 hours). Approval expiry is `approval_timeout`; active expiry remains `run_timeout`; expiry wins equal-timestamp approval races. Temporal execution timeout combines both budgets plus 180 seconds of headroom. Migration 0002 refuses active legacy runs; drain/version existing workflows before changing timer behavior.
- A versioned run-local policy refuses subsequent `record_note` calls after the first resolved denial, before approval publication or execution. Read-only tools and structured output remain available; a new explicit user turn resets policy by creating a new run. Unmarked Temporal histories retain their old decisions on replay.
- The only mutating tool is a PostgreSQL note, with effect and event committed in one transaction under a stable operation ID. The HTTP MCP integration is read-only. Arbitrary external writes are not exposed; future connectors must provide idempotency or actual reconciliation rather than relying on retries alone.
- Model/tool activities allow two attempts, provider SDK retries are disabled, and validation allows one retry. Request/tool/token limits are enforced across approval resumes. Failed provider attempts can incur usage not reflected in successful-response accounting; no exact monetary cap is promised.
- Operational telemetry contains only allowlisted run metadata and excludes content/exception bodies. Private PostgreSQL session data and Temporal history contain task content. No external trace export is enabled by default.
- One validated operator registry maps public provider/model aliases to private adapters, namespaced upstream models, explicit endpoints/authentication modes, and tool-calling/token capabilities. Responses, Chat Completions and Anthropic adapters use zero SDK retries. Unsupported selections/capabilities are rejected at agent create/update and new-run submission; no fallback occurs. Each run pins a content-derived immutable registration retained in PostgreSQL across config edits and restarts. Endpoints/credential references remain outside public contracts, events and traces. Local unauthenticated Chat Completions sends no authorization header or inherited OpenAI credential.
- Luna uses the immutable registration’s private reasoning default (`none`) at activity model construction. Legacy registration hashes remain valid; workflow coordination is unchanged. The official OpenAI transport pairs `httpx` client and transport over IPv4; `httpx` is an explicit production dependency.
- The small Python client/CLI uses public HTTP contracts, stable submission retry keys and ordered SSE replay. Startup creates only a missing local app-auth secret and never probes a paid model. Readiness distinguishes dependency observations from provider verification.
- Opt-in full HTTP acceptance uses isolated PostgreSQL schemas, task queues, API/worker processes and real MCP. A test-only SQLite transaction reserves every outbound Luna attempt before transport I/O, counting failures across restarts, with a fixed 20-attempt ceiling. This is a test guard, not a general billing subsystem. Synthetic evidence lives under docs/; Anthropic remains unverified.

Browser UI, specialist agents, additional connectors, sandbox execution and external publishing remain deferred. No sandbox backend was added because there is no shell/file execution tool.

### Inspection findings and implementation seams

- `schemas.py` currently restricts tools to three literals and output to `Answer(answer, value)`. `RunCreate` has no artifact references. Preserve those defaults and fields while adding owned contracts.
- `registry.py`/`Store.submit` already validate and retain immutable model registrations. Apply the same content-addressed retention pattern to tools, specialist selections, permissions and policies; retain installed handler versions as well as JSON metadata.
- `runtime.py` has a static FunctionToolset and connection-free workflow model selection. Installed PydanticAI 2.43.0 has prepared tool reconstruction and `DeferredToolRequests.calls`/`DeferredToolResults.calls`. Put new behavior behind a private adapter; do not serialize framework objects into public contracts or expose arbitrary function imports.
- `workflow.py` currently rejects all external deferred calls and manages approval pauses for a single run. Extend it with a versioned parent/child coordination path and a root-owned clock. A nested `agent.run()` inside a tool activity would not satisfy this design.
- `db.py` assumes every run owns a session and public idempotency key; `Store.finish` always updates session history. Child rows need explicit root/parent relationships and must never advance that session. `Dispatcher` currently assumes every run has its own start outbox entry; only roots will use this dispatch path.
- `RunUsage` counts successful model usage but does not reserve every actual request across retries. `model_adapter.py` disables SDK retries; retain that and place durable accounting around activity-side model requests and the outbound transport.
- `scripts/live_acceptance.py` already creates isolated DB schemas/queues, API/worker processes, SSE reconnects and safe evidence. It currently also inspects Store/events/notes directly, initializes tables from metadata, and cleans workflows through Temporal. Extend it to use migrations and public API observations for feature acceptance; keep process fault injection and infrastructure cleanup explicitly outside application behavior.
- `scripts/acceptance_worker.py` already reserves a SQLite row before each outbound request, but its global cap is hardcoded to 20, response maximum to 512, and model construction is monkeypatched. Retain old campaign behavior while introducing an explicit private transport-policy injection seam for the new campaign.
- Read-only environment inspection found Linux 6.14.0-37, Docker Engine 28.2.2 accessible through `sudo -n docker`, cgroup v2 with CPU/memory/PID controllers, Docker seccomp and AppArmor, and enabled AppArmor. `unshare` and `systemd-run` are installed; `bwrap`, `nsjail`, `runsc` and `podman` were not on the inspected PATH. The agent command sandbox itself failed before execution with a bwrap network-namespace error. Namespace usability for a worker is therefore not established. No sandbox image/service is implemented or validated. Existing Compose and app images make a separate Docker-backed job service the practical first backend.

### Operator registry and abstraction

Add `tool_registry.py`, an operator `config/tools.json`, and a small installed-handler catalog. A registration binds alias, immutable implementation version, schema version, schemas, effect/approval policy, permission set, input/output limits, timeout and retry/reconciliation policy. Canonical JSON determines identity; alias edits never mutate retained records. Reserve framework output names and `delegate` semantics against collisions. Configuration selects deployed code; it cannot provide source, import strings, a shell command, or an arbitrary MCP URL. MCP entries select an operator-configured connection and allowlisted remote tool/schema. Remote schema drift fails closed.

Keep `add`, `record_note`, and `convert_temperature` aliases, argument/result shapes and note approval semantics unchanged. Each registered alias resolves to a canonical permission/effect domain, so alias changes cannot evade denial. Agent tools form the root's permission ceiling; specialist tools must be a subset (excluding `delegate`) or configuration fails. Snapshot the complete parent/specialist graph, model and tool registrations, limits and denial policy atomically at root submission. Later specialist updates/removals affect future submissions only. Workers retain old implementations; a missing version fails with `tool_registration_unavailable`, never resolves to newer behavior.

Private interfaces should be small and typed: `ToolCatalog` (descriptor/select/retain), `ToolExecutor` (validate/execute/reconcile), `ArtifactStore` (put/read/grant), `BudgetLedger` (reserve/reconcile/fence), `SandboxBackend` (submit/status/cancel/collect), and a deferred-result adapter between owned task DTOs and PydanticAI. These are implementation seams for the included backends, not a plugin framework. Keep the existing model registry/client/CLI. No direct OpenAI SDK calls in fixture tools or delegation code.

### Storage, ownership, evidence and context

Use PostgreSQL-backed artifact bytes (`BYTEA` via SQLAlchemy LargeBinary) for this bounded milestone, behind `ArtifactStore`. It is already durable in this deployment and allows artifact bytes, hash, receipt, event and grant to commit together. Avoid adding S3 or a host shared directory. Proposed operator ceilings: 2 MiB per artifact, 8 MiB attached inputs per root, 8 MiB generated output per root and 256 MiB total workspace artifact storage. Reserve storage quota transactionally; duplicate idempotent writes do not charge twice. Retain referenced bytes until an explicit future retention policy exists; fail quota exhaustion rather than silently delete artifacts.

Associate API uploads with the existing single workspace principal. That API key intentionally has workspace-wide user access; do not claim per-user tenant isolation. Runs and tools receive narrower durable grants: root inputs explicitly attached by the user; child inputs a strict subset delegated by the root; child-generated output granted to that child and root. A sibling sees an output only when the root explicitly supplies it to a later child. Tools recheck grants on every read. No artifact ID, quoted prompt, session history or model-generated hash is a capability. Distinguish user download authority from model run authority in tests.

Add tables for tool registrations, run selections/specialist snapshots, artifacts and grants, root budgets/attempt reservations, operation records/results, root denial/approval records and delegation records. Child linkage is explicit in runs, with uniqueness on `(root_id, delegation_operation_id)` and a lifetime slot index 1 or 2. Artifact result slots are unique by `(producer_run_id, operation_id, output_name)`. An identical retry returns the committed artifact; a different digest in that slot is `operation_conflict`, not an overwrite. Preserve an operation's cached private result for post-commit recovery. Every effect commit locks the root before descendant/operation rows in a consistent order.

Use small input excerpts with source locators, never whole parent histories. Child context consists only of its pinned instructions, TaskSpec, artifact descriptors/explicit excerpts and its own tool/model turns. It cannot see parent hidden messages, sibling transcripts or unrelated session history. Keep detailed child history private; only the validated TaskResult enters the parent context. Children never write SessionRow. For new runs, construct session continuation from a compact owned completed-turn summary plus verified refs (at most 16 KiB/turn); preserve the old 250 KiB session ceiling and legacy history decoding. Refuse oversize structured results explicitly or externalize full content into a report artifact with an explicit summary/truncation indicator. Never silently drop evidence.

Target limits: ordinary tool result at most 8 KiB, root/child working model context at most 48 KiB UTF-8 before every request, with schema overhead accounted separately by the budget adapter. No raw artifact bytes in Temporal payloads. Generated code is at most 16 KiB and is durably staged as a private code artifact by an activity before sandbox submission; workflow arguments carry its ID/digest. Provider-returned text necessarily appears in private model activity history, so do not promise that code never appears there. Events/traces exclude it. Fixture text is untrusted data, including instructions embedded in repository files or Markdown.

### Concrete sandbox backend: isolated Docker job service

Implement one `DockerJobServiceBackend` talking to a separate operator-owned `sandbox-service`, with a fixed minimal Python job image pinned by digest. The existing Docker deployment supports this choice; do not assume host `unshare` is secure or usable. The API and worker never receive the Docker socket, Docker TCP access, sudo, privileged mode or host filesystem mounts. Generated code never runs in an API/worker subprocess. A subprocess used by the trusted job supervisor is inside the job container only.

The service is a separate control-plane trust boundary. Only this service has daemon access; its narrow authenticated internal interface accepts bounded bytes, fixed job IDs and limits that may only be lowered. It has no Docker API proxy, exec endpoint, arbitrary image/entrypoint/options, caller-selected mount/network/user/capabilities, package installation or URL fetching. Do not attach it to an externally published port. Give workers a service-specific credential, never propagate provider/app credentials into jobs. Its ownership check restricts status/cancel/collect to jobs issued to that service principal. Requests/results use explicit size limits and schemas.

This service's daemon access is privileged and must be isolated from user code: it is not a way to put a socket inside workers. Run it separately from app code, audit the fixed container-spec builder, and use a dedicated daemon/host when deploying beyond the local single-operator environment. Docker shares a host kernel and this is not a VM-strength sandbox. Existing flags and daemon version are availability observations, not security acceptance; implementation must verify current supported engine/kernel hardening before enabling untrusted jobs. If safe controls cannot be established, leave Python analysis unavailable and report the unmet acceptance criterion.

Each job has a read-only minimal root filesystem, private PID/IPC/mount namespaces, `network=none`, no host namespaces/devices/binds/socket, AppArmor confinement, enforced seccomp profile, no-new-privileges, no core dumps, standard-library-only Python, and generated code running as an unprivileged UID with no effective/permitted/ambient capabilities. Container/user code cannot reach the broker, DB, MCP, provider or metadata endpoints. Python `-I` helps avoid ambient configuration but is not the isolation boundary.

A small trusted supervisor inside the image accepts a bounded framed input stream, installs root-owned read-only inputs, creates bounded tmpfs scratch/output, then launches generated code under a different unprivileged UID. Any minimal UID-transition capabilities belong only to trusted initialization and are dropped; none reach generated code. The supervisor has separate ownership/protected control descriptors so generated code cannot kill it, replace inputs or forge its exit accounting. Code stdout/stderr go to separately bounded pipes. It enforces 20 seconds execution and an absolute 30-second container lifetime including input/output handling; expiry exits PID 1 and ends all descendants even if a child forks/changes process group or the service disappears. Prove this boundary before enabling the tool; do not rely only on worker cancellation or a killable same-UID timeout process.

Fixed job ceilings: 1 CPU, 256 MiB RAM with no additional swap, 64 PIDs, 64 MiB scratch/output tmpfs, 8 MiB input bytes, 64 KiB combined stdout/stderr, 4 outputs with 2 MiB/file and 4 MiB aggregate. Apply CPU/memory/PID controls in Docker and file/descriptor/process limits in the supervisor. Limit service concurrency to two jobs globally and one per root. No image pulls on the tool path; operator builds/loads the pinned image. Missing image, daemon, enforcement controls, authentication, healthy supervisor or reaper means `sandbox_unavailable` before execution. No weaker fallback.

Transfer input/output bytes through bounded service streams, never a worker host mount. Broker/supervisor output collection accepts only declared regular files under the output directory, opened without following links; reject traversal, symlinks, hardlinks, devices, duplicate names and size overruns. Never unpack an untrusted tar on the host. Hash bytes during collection, then the worker activity atomically publishes artifacts under the current root fence. Keep full stdout/log content out of events/traces; a bounded authorized report artifact may contain synthetic diagnostics.

Persist broker job IDs, root/operation IDs, request digest, container identity, deadline and result receipt before/around creation. Use a fixed container name plus labels derived from the durable operation; duplicate identical submits attach to the original, changed digest returns conflict. Reconcile daemon create acknowledgement loss by name/labels; never create a second job while the first may exist. Job image restart policy is `no`. Persist results until collection acknowledgement; if the container died before a result was stored, report a typed lost-result failure instead of pretending success or silently executing again. Service restart and periodic reaper clean only owned jobs. Cancellation is idempotent, requests immediate job termination and reconciles eventual cleanup. The independent in-container lifetime remains the last bound during broker/worker outages.

Docker's [resource controls](https://docs.docker.com/engine/containers/resource_constraints/), [network-none mode](https://docs.docker.com/engine/network/drivers/none/), [seccomp](https://docs.docker.com/engine/security/seccomp/) and [AppArmor](https://docs.docker.com/engine/security/apparmor/) support the proposed controls; the fixed service/supervisor design and adversarial acceptance below are application decisions. [Docker Engine security](https://docs.docker.com/engine/security/) explains why daemon access must remain an operator trust boundary.

### Delegation, identity and recovery

Use a versioned root workflow and `ChildRunWorkflow`, registered by the existing worker. Keep legacy `RunWorkflow`/activity names available for retained histories; dispatch new runs using a persisted execution version. Do not rename an existing activity under a replaying history. Use additive migrations and an explicit drain/version rollout, preserving current DB volumes and uncommitted files.

A model-produced `delegate` becomes an external deferred call, not a nested model request. The adapter translates the recorded request into TaskSpec. A storage activity validates selected specialist, grants, depth, root fence and remaining lifetime slots; transactionally creates or retrieves the delegation/child row and emits `child.queued`. Child ID is a deterministic UUID/hash of root ID and the durable delegation operation identity. Workflow ID is `child:<root-id>:<operation-hash>`; ID reuse policy rejects a new execution for the same identity. There is no child start outbox command. The parent uses `start_child_workflow`, awaits its started event, then waits on its result while servicing control messages. See [Temporal child workflows](https://docs.temporal.io/develop/python/workflows/child-workflows).

Define operation identity from persisted run ID, agent-loop round/model-response identity and tool-call index/ID; never trust the model's raw call ID alone across rounds. The normalized argument digest is immutable for that operation. Replayed identical calls recover the same child/result and do not consume another slot; mismatched arguments fail. Distinct new delegation calls consume lifetime slots even when earlier children failed or were cancelled. A third child, child delegation or substituted specialist is refused before child I/O. For one response containing two delegations, process them sequentially in recorded order. Validate the whole deferred batch before starting work; process approvals before launching a deferred child so denial is inherited. Mixed approval/call results must resume the original model turn with the corresponding IDs exactly once.

Child input is its persisted child ID; its load activity retrieves the snapshotted config and selected input grants. Child workflow performs deterministic coordination, with model, tool, artifact and DB I/O in activities. Do not read operator files or perform DB lookups in workflow prepare hooks. Retain existing TemporalDurability where it fits, with the adapter providing immutable selection metadata and activity-side guards. If explicit activity wrappers are needed, use stable versioned names and keep framework types private; no whole nested child agent loop hidden inside a tool activity.

On completion, an activity validates and commits the child's TaskResult, events, refs and usage attribution before the child returns a small owned result/ref. A lost child completion or parent resume acknowledgement reloads that committed result. Child failures produce typed TaskResult failures; they do not auto-respawn. Parent may explain partial evidence, but must label failure/incompleteness and must not claim successful comparison. Root budget/time/cancellation failure is fatal to the entire tree, not recoverable by another child. Shared resource limits remain authoritative even if the model asks to continue.

Explicit root cancellation cancels child handles with bounded waiting; set `ParentClosePolicy.TERMINATE` as the fallback for unexpected parent closure. This does not guarantee activity cleanup, so durable fences, the outbox/reconciler and sandbox deadlines remain necessary. Extend Dispatcher reconciliation to distinguish root dispatch from recorded child intent, describe recorded child IDs, recover terminal results and mark children left after a closed root. A queued child intent with no started child while the root is active is resumed by the parent history, not independently started by Dispatcher. Root success requires every started child to be terminal, all accepted outputs committed and no unresolved operation. Root cancellation can be publicly terminal while `cleanup_state=pending`; later cleanup events remain replayable. Update SSE/client wait behavior so callers can opt to wait for cleanup and a stream does not close before pending cleanup is reported.

### Root-owned budgets, denials, approvals and cancellation

One durable root budget row is authoritative for the parent, children, tool retries, model validation retries and approval resumes. Local PydanticAI RunUsage/UsageLimits remain secondary guards. Root configuration defines total allowed physical model attempts, distinct tool invocations and token allowance; child ceilings can only reduce its access to the remaining root allowance. No child gets a fresh allocation by copying a counter. Admission limits count root trees; child slots and sandbox capacity are separately bounded without competing with their own root's single-session gate.

For each model activity, use stable logical request identity plus Temporal activity attempt and a persisted physical-dispatch ordinal. Before any provider transport I/O, atomically reserve one request attempt and a conservative input-token allowance plus the actual output cap under a root lock. Include instructions, history, tool schemas, typed output schema and protocol overhead in the adapter's reservation. Implement/document a conservative text/token bound for each enabled provider; unsupported content/accounting capability fails before I/O. For the Luna text-only campaign use a deliberately conservative UTF-8-byte-based input reservation plus tested serialization overhead; reported usage exceeding the reservation exhausts/fences the root and records the overrun. This is an operational bound, not a claim that every provider bills identically.

Persist reservation states (`reserved`, `sent`, `reconciled`, `uncertain`) and the private logical response cache. A successfully persisted response can be returned after activity replay without another request. A crash after dispatch but before response persistence leaves the attempt and full token reservation charged; a retry requires a new physical reservation. A crash between reservation and send may overcount; never refund an ambiguous attempt or reuse its slot to send again. Valid successful usage reconciles token allowance exactly once; request attempts never decrement. Failed/unknown usage retains its reservation. Zero SDK/transport retries and no redirects remain required; any intentional extra send must pass both the root ledger and campaign guard. If either ledger is unavailable, stop before I/O. Budget failure finalization must use a storage-only path, requiring no model request.

Tool invocation admission uses a stable operation record and consumes root `max_tool_calls` once per distinct requested call, including denied/invalid-argument attempts and delegation. Physical tool attempts have a separate durable count and at most two attempts per operation; retries reuse cached committed results where possible. Retryable reads can execute again; mutations require idempotency/reconciliation. Reserve artifact/sandbox quotas before those effects. Root budget API distinguishes logical calls, physical attempts, uncertain tokens and reported tokens. Budget checks and root cancellation/policy fences run again at effect commit.

The root workflow alone owns the existing cumulative active-time and approval-time clocks. Execution is sequential across the tree: while a child runs, parent generation and other tool activity batches are paused, but root active time continues (including queueing, model/tool/storage execution, backoff and worker downtime). Child active ceilings only shorten that interval. A child approval request is persisted under the root and signalled with a monotonic wait generation. The root validates the pending approval via an activity, enters a durable wait, pauses its active clock and acknowledges the wait to the child. Until acknowledgement, time remains active. No branch may perform model/tool work during the paused interval. Decisions are persisted and routed through the root; after resumption is durably coordinated, the root restarts its active clock and signals the child. Replayed/delayed wait signals cannot reopen a resolved wait. Charge the union of approval waits once, including root downtime, against the single finite allowance; expiry wins equal-timestamp decision races. Snapshot timer transitions/deadlines through activities for budget API visibility; workflow history remains the source of deterministic elapsed time. Children never reset either root clock.

Generalize the existing note-denial policy into a durable root denial set keyed by canonical effect permission domain. A denial anywhere in the tree is inherited by parent, existing children and future children. Persist it atomically with the immutable exact-call decision; check before approval publication, before tool execution and under the root lock before effect commit. Alias changes, different call IDs, changed arguments and fresh children cannot clear it. A fresh explicit user turn creates a new root and policy. Read-only evidence collection and permitted local artifacts remain usable after a note denial. Only explicitly effectful operator registrations require approval; input upload itself is an authorized API action.

Approvals bind origin run, canonical tool registration, operation identity and normalized arguments. Pending child approvals are listed and decided on the root endpoint; immutable decisions survive restart and duplicate/out-of-order signal delivery. Approval and denial do not grant additional artifact/tool capabilities. If several calls in a batch share an effect domain, a resolved denial fences the other uncommitted calls as well; approval cannot override that root policy.

Cancellation locks and fences the root first, marks active descendants cancelled, prevents new reservations/child creation/approval publication and artifact/note commits, and writes durable cancellation commands for workflows and jobs. Already committed effects remain receipts; there is no claim to undo a completed provider request. Post-cancel provider responses may settle accounting but cannot publish output. For broker dispatch already in flight, cancellation is reconciled by operation ID and the independent job deadline; no accepted late artifact appears. Concurrent approval, cancellation and effect commit have a clear root-lock order: only a commit preceding cancellation survives. Reconciler cleanup is retryable and does not replenish budgets. Read-only in-flight requests may finish, but results are fenced from application success.
